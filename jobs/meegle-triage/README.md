# Meegle 分诊任务

## 当前链路

GitHub 新建 Issue → AnyCross 验签并创建或复用来源池单 → 持久事件队列 →
ASTRA 单单翻译、分类及派单 → 回读正式目标与人员、正文、来源关联 → Lark 三行通知。
正式消息只含标题、GitHub 链接和最终 Meegle 链接，不发来源池链接或 HTML 图片。

AnyCross 旧 30 分钟 GitHub 查询已停止；Hermes 旧两小时整池扫描已暂停。
保留官方任务记录及其创建者授权，仅复用官方执行入口处理当前事件。
旧积压不清空，也不会因新事件重新扫描。业务代码只属于本任务，不修改 Core。

宿主事件服务使用 Linux Python 3 标准库和 SQLite；执行端复用 Hermes Python、
Meegle CLI、Lark CLI 和现有创建者授权，无新增公共依赖。运行数据与凭据不进 Git。

## 文件与运行入口

- `event_service.py`：认证、仓库白名单、持久入队和串行工作线程；提交成功后才返回 202。
- `queue_store.py`：事件按仓库与编号唯一保存，目标和通知分阶段持久保存。
- `runner.py`：核对来源身份，调用原分诊规则，独立回读后发送并回读消息。
- `event_instructions.md`：单事件范围、翻译、保留人工人员、低置信人工复核及输出约定。
- `anycross_prepare.js` / `anycross_receipt.js`：建池成功后提交事件，核实持久接收。
- `publish.py`：只发布明确指定的本任务文件；验证通过才原子切换 `current`。

运行根由运维设置，内含 `service-config.json`、`runner-config.json`、
`event-prompt.txt`、`state/events.sqlite`、`state/output/`、`releases/` 和 `current`。
真实仓库路由、群、人员、存储任务 ID、项目、密钥只保存在受保护配置。
服务配置包含监听地址、端口、令牌、状态目录、执行命令、仓库路由和人工复核群。
执行配置包含项目、来源类型、功能建议类型、原任务 ID、提示词和输出目录。
`pm_follower_userkey` 指向经实时查询唯一确认的在职 PM「77」账号，属于受保护身份配置。
提示词由受保护原规则加本目录事件规则组成，不随代码发布覆盖。

服务由 `hermes-meegle-triage.service` 托管；宿主仅绑定 Docker 私网，
HTTPS 经已有反向代理进入 `/hooks/meegle-triage`，使用 Bearer 验证。
`GET /hooks/meegle-triage/health` 检查进程，认证后的
`GET /hooks/meegle-triage/status/<owner:repo:number>` 回读单事件状态。
健康或 HTTP 202 均不代表业务处理完成，必须查看 `done`、正式目标和通知回执。

## 重试与边界

重启保留队列并恢复在途事件；同一仓库和编号只由一个工作线程处理。
执行端持有跨进程锁，避免服务重启与残留执行重叠。
通知失败复用已核实目标；保存发送回执后重试仅回读，不再次发送。
自动失败重试最多三次，间隔至少一分钟；最终失败记录保留，并尝试向复核群提醒。
人工复核不硬派，不向业务群发送缺失最终目标的消息。赞助保持过滤。

AnyCross 建池存储不是原子锁：极端同时首次投递仍可能产生重复来源池单。
接收端对同一 Issue 的不同来源 ID 返回 409，不覆盖原事件、不静默再建正式目标。
不承诺跨 GitHub、AnyCross、Meegle、Lark 的绝对一次执行；发送与写收据之间的
极短崩溃窗口仍受 Lark 自身去重时限约束。旧重复池单和历史积压不在本次清理范围。

## 负责人字段规则

2026-11-13 只读检查了 6 张已有正式 Bug 单。6 张均在显示名称为
“BUG负责人”的 `watchers` 字段中填有人员。“BUG负责”是另一个近似名称字段，
不能直接替代。“BUG关注人”也单独存储。

原提示词要求精确填写“BUG负责人”，同时又禁止 `watchers`，导致任务自行停止处理。
这证明任务规则冲突，不能据此推断 Meegle 平台拒绝写入。

修正规则以实时元数据中的精确显示名称为准。内部名称 `watchers` 及其“系统通知”
描述都不构成禁用理由。人员仍须解析成唯一账号，按字段类型写入，再回读核对。
不得仅更新 Assignee 角色或其它近似字段。

## 规则修改与恢复

配置修改前，将完整任务存储备份到受保护持久卷的 `backups/`。
使用运行环境中官方 `cron.jobs.update_job`，只更新目标任务的 `prompt`。
随后用 `get_job` 回读，比较其它设置和其它任务，确认均未变化。
不直接改任务存储文件，不重启网关，也不修改 Core 或公共扩展。

恢复时，从备份提取该任务的原提示词，再通过同一官方接口只恢复 `prompt`。
不要整份覆盖任务存储，以免丢失后续调度或其它任务的变化。

## 单任务发布与核验

只上传下列发布器白名单文件到独立暂存目录，不递归上传工作区、任务运行根或授权目录。
在 Linux 用以下命令验证并切换代码：

```sh
python3 /path/to/staged/publish.py --job meegle-triage \
  --source /path/to/staged --root /path/to/protected/jobs/meegle-triage
```

发布器先复制完整白名单、运行事件测试，再切换 `current`，不碰配置、调度和业务状态。
服务工作目录与执行端命令均指向 `current`；切换后重启本任务 systemd 服务，
回读健康、路由、队列和实际目标。不得重建公共镜像或发布其它任务。
失败验证不切换；恢复代码时原子切换到已有完整版本，再重启本任务服务。
不要恢复旧数据库来回滚代码，避免丢失已完成目标或消息回执。

```sh
python3 -m unittest discover -s jobs/meegle-triage -v
git diff --check
python3 scripts/check_scaffold.py
journalctl -u hermes-meegle-triage --since today --no-pager
```

日志及截图只存忽略目录 `artifacts/github-event-triage/`，不提交内部聊天或人员数据。
本地和 Linux 临时环境覆盖发布失败保持旧版本、状态/配置保留及其它任务不变；
这不等同于承诺所有公共镜像升级已经通过隔离验收。
