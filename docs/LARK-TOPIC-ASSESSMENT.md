# Lark 原生话题评估（Issue #5）

日期：2026-10-01。范围：已部署官方 Hermi、授权测试群；只做验收与方案评估，没有实现、安装或启用移植代码。

## 结论

已有原生话题的带 @ 连续回复、精确引用文本和两个话题隔离已通过真实链路。普通群聊首次 @ 自动开题不具备；本轮已有话题内不带 @ 的一条后续消息也没有进入处理会话。

**首选下一步是 Deploy 的薄平台扩展评估/实现，而非先改 Core。** 通过官方 `ctx.register_platform` 注册一个继承当前 FeishuAdapter 的适配器，在入站批处理前归一话题、在发送时处理原始消息锚点与服务端话题标识。保留官方连接、鉴权、工具、会话存储与普通收发。公开注册能力已经在临时环境核实，但这种派生方案依赖固定基线的 Feishu 内部接缝，不能宣称享有完整的上游升级兼容保证。

`pre_gateway_dispatch` 与处理生命周期钩子单独不够，不等于必须修改 Core。只有下一阶段证明平台扩展无法保持身份、批处理、排队和会话连续性，或者明确要求完全不依赖私有接缝，才提炼通用 Core 扩展接口。当前不建立未经必要性证明的 Core 实现任务。

## 归属与验收边界

- 复用首次 @ 原始证据，没有再次发送首次群 @。复用两个已有测试话题，没有要求用户新建话题。
- 测试请求使用已有授权的 CLI 用户身份发给 Hermi；所有机器人回答均由当前受管 Hermi 应用发出，容器网关日志与持久会话再次核对。没有用 CLI 默认应用机器人冒充 Hermi。

## 真实结果

| 检查 | 结果 | 本地证据 |
| --- | --- | --- |
| 首次普通群 @ | 原请求/回答只有普通引用关系，回答无原生 thread_id | `evaluation.json` 中首轮记录 |
| A1：在话题 A 约定代号与颜色 | Hermi 回“A已记住。”，仍在原生 A | `a1-send.json`、`a1-readback.json` |
| A2：不带 @ 的后续消息 | 平台收到消息；超过 3 分钟未见回答，持久会话无该请求 | `a2-send.json`、`q1-thread-readback.json`、`session-readback.json` |
| A3：带 @ 回忆 A | 返回 A 的代号与颜色；引用锚点本身没有这些信息 | `a3-send.json`、`a3-readback.json` |
| B1/B2：独立话题 B | 两次返回 B 的代号、颜色“未约定”，没有 A 的代号/颜色 | `b1-readback.json`、`b2-readback.json` |
| Q1：引用 A1 的机器人回答 | 精确复述“A已记住。”，再返回 A 的代号和颜色，原生话题与父消息均正确 | `q1-request-readback.json`、`q1-thread-readback.json` |
| SQLite 会话隔离 | A/B 为两个不同会话键；各自只有自己的代号；工具调用均为 0 | `session-readback.json` |
| 运行源码一致性 | 5 个相关源文件与容器 SHA256 一致 | `source-runtime-hashes.json` |

Q1 未传 `reply_in_thread`，平台仍把对既有话题内消息的回复归入原话题，回读请求自身已有 thread_id。因此它证明“引用话题内消息仍回到该话题”，**不证明**“客户端在主群发送一个没有 thread_id 的引用，机器人主动重路由回话题”。后一个精确输入形态未覆盖。

A2 的事实是未回应、未进入处理会话。官方 `_admit` 会在 require_mention 生效且没有 @ 时拒绝，运行环境变量未覆盖该默认值，但未逐项核实所有群级配置；日志没有逐条拒绝原因，故不能只凭无回答证明每一层的丢弃位置。

所有请求、回答、父消息、根消息和话题 ID 只保存在本地证据。6 条必要用户测试消息、5 条 Hermi 回答；旧话题中的历史回复不计作当前版本验收。

## 旧 CN 的最小行为契约

参考旧 HEAD `ac0b6703c0`；旧源码未修改、未导入新工程。

1. 群内明确 @ 受管机器人后，原始消息成为新讨论锚点；已有原生话题优先沿用；引用已受管话题时恢复同一讨论。
2. 第一次模型处理前必须确定稳定会话标识。第一次输入、首条进度、正式回答和后续入站不能分别落在群会话、消息根会话、服务端话题会话中。
3. 首次出站通过原消息 ID 的回复接口请求 `reply_in_thread=true`。真实原生话题只能由服务端返回及回读确认；本地把 message_id 称为 topic 不代表已创建。
4. 成功返回后，把服务端 thread_id、root_id 与稳定讨论键关联；映射按应用、群、讨论隔离并持久化。后续入站在批处理/会话排队前解析同一映射，处理回读与后续消息的竞态。
5. 引用正文与会话归属分别处理。普通引用关系不能无条件当作原生话题；没有明确邀请时不接管群内普通讨论。
6. 首次创建或发送失败，不改发群顶层消息来伪装成功；必须保留失败证据。重试需要幂等，不能重复建题。

## 官方路径与钩子判断

| 顺序 | 实际路径 | 含义 |
| --- | --- | --- |
| 1 | Feishu `adapter.py:2117` 调 `_admit`；`:3383–3416` | 群权限与 @ 门控在插件分发钩子之前；被拒消息到不了 pre_gateway_dispatch |
| 2 | `adapter.py:2633–2674` | 只认原生 message.thread_id；parent/root 用于引用正文与锚点 |
| 3 | `adapter.py:2676–2684`、`:2937–2942` | 先做文本/媒体批处理；不同首次 @ 若还在无话题群会话中，晚改键无法撤销已经发生的合并 |
| 4 | `base.py:4015–4027` | 先计算会话键并领取处理中位置 |
| 5 | `base.py:4503–4508` | 先拍下发送话题信息，再调用 on_processing_start，随后进入网关 handler |
| 6 | `run_inbound.py:111–145`、`:270–279` | pre_gateway_dispatch 才执行，早于网关鉴权；公开返回只支持 skip、rewrite 文本、allow |
| 7 | `adapter.py:3747–3769` | 有 thread metadata 才 reply_in_thread；无 reply anchor 时按 thread_id 发送 |
| 8 | `base.py:4573–4596` | on_processing_complete 覆盖成功/失败/取消；是 adapter 可覆盖方法，不是任意注册同名插件 hook 即生效 |

所以不能在 pre_gateway_dispatch 里随手修改 source.thread_id：底层排队键与发送信息已经取过，可能形成“模型上下文进入新键、最终回答仍用旧路由”的不一致。on_processing_start 同样太晚。生命周期方法适合每轮进度状态的初始化/收尾，不能独立解决首次开题及早期路由。

## 推荐的 Deploy 平台扩展方案

官方公开入口 `PluginContext.register_platform` 在 `hermes_cli/plugins.py:808–837`。官方 bundled 平台通常延迟加载（`plugins_discovery.py:293–297`）；显式同名注册会替换已有条目并清除未执行的延迟加载器（`platform_registry.py:281–299`）。本轮在独立临时 home 调用真实注册入口，确认替换 factory、保留原平台配置/鉴权/独立发送字段、取消 pending loader；未连接第二个网关。证据 `registry-probe.json`。

拟采用明确启用的 `extensions/lark-topics/` 平台扩展，注册平台名仍为 feishu，继承官方适配器；不重写整套传输。载入时取得官方完整平台条目，只替换工厂，保留鉴权、配置桥接、独立发送和其他平台属性。固定当前 Core 基线；工厂、依赖或接缝不满足时明确失败，不静默回落为另一套话题行为。

最少需要三处行为接缝：

- **批处理前归一化**：在官方 `_dispatch_inbound_event` 前计算稳定讨论键并记录原生发送目标，之后再交还官方批处理与 `handle_message`。首次 message_id 与后续 thread/root 别名必须归到相同键。不能只覆盖 public handle_message 而忽略更早的批处理。
- **出站锚定与回读**：在 Feishu 发送边界把稳定讨论键解析为真实发送目标；尚未建题时以原始消息为锚点请求原生回复，成功后绑定服务端 thread/root；之后复用官方收发与错误处理。不把本地 message_id 当服务端 omt_* ID 直接发送。
- **成员参与（单独增量）**：保留官方权限拒绝与自回声保护，仅让已参加的本话题成员按约定免 @；未参加的群消息仍不接管。该接缝位于 `_admit`，不能靠更晚的 pre_gateway_dispatch 恢复被丢弃的消息。首次自动开题最小版本不必同时恢复完整旁听/队列。

风险：上述三个 Feishu 接缝和 bundled 类导入不是公开稳定插件 API；公开工厂注册不保证内部方法升级不变。每次 Core 更新须针对早期批处理、第一轮到后续轮、不同话题、权限拒绝和失败路径做行为回归。此处是可行设计，尚未编写/部署，也未证明原生自动创建与重启恢复。

若该薄扩展不能满足后续实证，最小通用 Core 缺口应围绕“**批处理/会话占用之前的路由转换**”与“**发送结果确认后的话题绑定**”定义，而不是只在首答发送时加开关。单纯首答成功后才替换会话键会割裂第一轮上下文。公开钩子必须保留鉴权、失效/取消语义及原始发送目标；团队选择规则仍留在 Deploy。
